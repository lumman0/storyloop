# Source-driven story design

> Historical planning record: paths and commands describe the pre-split repository, not current installation instructions.

The player-visible prologue and ordinary turns are generated by the selected model. A scenario package supplies source-grounded facts, character constraints, setup choices, and loose milestones; platform code contains no winter-show story dates or prose. The existing scripted campaign runtime remains readable for older saves and other packages.

## Package contract

An optional `story_blueprint.json` selects the source-driven runtime. It identifies the source document, exposes a package-defined setup form, and contains opening context, facts, and milestones with source references. Facts can name active days and recall keywords; each turn retrieves the current day's material, general rules, and earlier material explicitly mentioned by the player. A milestone has a source-authored timing hint, not a fixed passage or mandatory sequence of `continue` buttons. One milestone may mark the model-generated ending. Missing blueprint means legacy behavior. Package fingerprinting includes the blueprint. Upload validation checks bounded references, actor IDs, setup IDs, and text lengths.

A private validation package converts a source DOCX into setup choices, facts, character slots, and milestones. Character and event details are package data. Where a source contradicts itself, the package records the chosen interpretation and source references for author review; the engine never chooses a scenario-specific date.

## Save and opening

The catalog exposes optional setup metadata. The client sends validated setup values when creating a save. The runtime seeds save-scoped player profile, tone, and actor profiles. It calls the configured model once to generate a second-person prologue from the source-grounded opening context and selected profile. The generated prologue and setup are stored with the save; resume never regenerates them. Failed generation does not publish an unusable save or charge a player for a nonexistent story. Existing packages retain their opening behavior.

## Turns and progress

For blueprint saves, each player action receives one narrative-model call. The model sees the full latest player action, end of the last visible scene, relevant source facts, the source author's conflict resolutions, current milestone hints, player memory, and separately labeled NPC-owned context. The model writes the complete prose, three situational options, and a small optional ledger of witnessed events and speaker-owned memories. The runtime stores authoritative player actions and NPC observations, but does not splice other prose into the result. No fixed `continue` sequence is used. Milestones can become relevant as time and prior events permit; the model decides how they appear in prose without overriding player agency. The runtime validates speaker IDs and scopes stored memories to the recipient. Semantic leakage inside generated prose remains a model-quality risk. The beta multi-agent and legacy scripted paths remain intact.

## Quality and compatibility

The harness must not truncate or replace generated prose. Recent context prioritizes the ending of the previous scene and does not keep stale goals after the player changes activity. Group scenes persist a participant's own speech or a minimal witnessed summary to that participant, including those beyond the private-context focus limit. Day and period come from save state and source data and are included as authoritative prompt values; prose-level contradiction detection is a later quality gate. Old saves retain their package version and response history. Private source packages, credentials, and original documents are never committed to the public repository.

Verify the source-driven path with a focused offline scenario and a new source-driven save. A real-model literary comparison with a private reference transcript requires separately authorized API egress; tests cannot claim prose parity without it.
